# Maintaining the formalization artifact

Use the pinned `lean-toolchain`, `lakefile.toml` and `lake-manifest.json`. Preserve the submitted artifact when working on changes; the existing `audit/` directory is inherited build evidence, not a report regenerated by this supplement revision.

From `lean/`, compile changed proofs with:

```bash
lake exe cache get
lake build GD
```

Run `lake env lean GD/Audit.lean` in a separate working copy to export the compiled environment. This overwrites `audit/lean_declarations.json`; no supplied full runner automatically refreshes all provenance, coverage and graph files. `python tools/check_snapshot.py` only checks consistency against existing provenance and should fail after proof inputs change until a genuinely new build/export has been reviewed and recorded.

For a new or changed manuscript result, review its full `GD.PaperTargets.*` type, provide a `GD.Paper.*` theorem proving that exact target, and update `docs/statement_inventory.json` and the correspondence tables together. Record extra hypotheses and scope limitations. A proposition definition is not a proof. Compare the final PDF's mathematical statement before updating its recorded hash; a matching filename or new hash alone is insufficient.

Inspect all named theorem axiom closures and project proof/type references. The permitted foundations are `propext`, `Classical.choice`, and `Quot.sound`. Do not replace missing arguments by `sorry`, custom mathematical axioms or unsafe evaluation. Keep the external smooth-convex certificate boundary explicit.

Only record successful new provenance after a completed build/export, with all nested `GD/**/*.lean` sources included and inputs unchanged during the run. Retain actual toolchain versions, exit codes, logs and timing methodology. Label incremental build timings as incremental. Review generated dependency graphics whenever proofs or the mathematical dependency registry change.
